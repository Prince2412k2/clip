# Spec: clippy v1 — targeted cross-platform clipboard sender

**Date:** 2026-07-13
**Status:** draft (awaiting approval)
**Supersedes:** `DESIGN.md` for v1 scope. v1 uses a **targeted send** model (pick one
target machine) over **unified HTTP on the Tailscale network**, NOT the P2P SSH-gossip
model in DESIGN.md. DESIGN.md remains the north star for later versions (gossip,
anchor, history, TUI, iOS Shortcuts tiers).

## Summary

A daemon (`clippy`) runs on each machine in a personal Tailscale fleet. It watches the
local clipboard and auto-pushes every change to a **user-selected target machine**,
where it is written straight onto that machine's system clipboard. Files are saved to a
configured folder instead. A CLI selects the target and toggles syncing on/off. A small
static webapp (served by the daemon) lets a phone drop text/files/images to a
configurable target. Text, images, and files up to 20 MB are supported. Linux and
macOS in v1; Windows later.

## User stories

### US-1 — Copy here, paste there (P1)
As someone at machine A, I copy text or an image and it appears on machine B's clipboard
with no further action, so I can paste it in B immediately.
*Independent test:* with A's target set to B and sync on, copy text on A; within a few
seconds the same text is on B's system clipboard.
- **Given** A's target is B and sync is on, **When** I copy "hello" on A, **Then** B's
  system clipboard contains "hello".
- **Given** A's target is B, **When** I copy a PNG screenshot on A, **Then** B's
  clipboard holds that image, pasteable into an image editor.

### US-2 — Send a file (P1)
As someone at machine A, I copy/select a file (≤ 20 MB) and its bytes arrive on machine
B saved into B's configured receive folder, so I can open it there.
*Independent test:* copy a 3 MB file on A; it appears in B's receive folder with the
original name.
- **Given** A→B and a 5 MB file copied on A, **When** sync runs, **Then** the file
  exists in B's receive folder with its original filename and identical bytes.
- **Given** a 30 MB file copied on A, **When** sync runs, **Then** it is NOT sent and
  the user is informed it exceeded the cap.

### US-3 — Choose the target (P1)
As a user, I list the machines on my tailnet and select which one my copies go to, so I
control the destination.
*Independent test:* run the CLI list command; see tailnet peers; select one; the
selection persists across daemon restart.
- **Given** three online tailnet peers, **When** I run the select command, **Then** I
  can pick one and it becomes the active target.
- **Given** a selected target, **When** the daemon restarts, **Then** the same target
  is still active.

### US-4 — Turn it on and off easily (P1)
As a user, I toggle syncing on/off with one command, so I can stop broadcasting
sensitive copies without killing the daemon.
*Independent test:* toggle off, copy something, confirm nothing is sent; toggle on,
copy, confirm it is sent.
- **Given** sync is on, **When** I run the off command, **Then** subsequent copies are
  NOT sent and status reports "off".
- **Given** sync is off, **When** I run the on command, **Then** subsequent copies are
  sent to the target.

### US-5 — Drop from a phone (P2)
As a phone user on the tailnet, I open the daemon's webapp, choose a target machine, and
drop a file/image or type text; it lands on that machine's clipboard/receive folder.
*Independent test:* from a phone browser, open the webapp over Tailscale, pick a target,
upload an image; it appears on the target's clipboard.
- **Given** the webapp open on a phone, **When** I select target B and drop an image,
  **Then** B's clipboard holds that image.
- **Given** the webapp, **When** I type text and submit to target B, **Then** B's
  clipboard holds that text.

## Functional requirements

**Clipboard watch & send (source side)**
- FR-001: The daemon MUST detect local clipboard changes for text and image content
  while sync is enabled.
- FR-002: On a detected change, the daemon MUST send the content to the currently
  selected target machine automatically (no user action per copy).
- FR-003: The daemon MUST support sending a copied file's bytes and original filename
  when a file (rather than text/image) is on the clipboard.
- FR-004: The daemon MUST NOT send any content whose size exceeds 20 MB, and MUST make
  the skip visible to the user (log/notification).
- FR-005: The daemon MUST deduplicate by content hash so an unchanged clipboard (or a
  repeated watcher fire of identical content) is sent at most once.
- FR-006: The daemon MUST prevent send/receive echo loops: content written to the local
  clipboard as a result of *receiving* MUST NOT be re-sent by the watcher.

**Receive side**
- FR-007: On receiving text or an image, the daemon MUST write it to the local system
  clipboard.
- FR-008: On receiving a file, the daemon MUST save it into a configured receive folder
  using the original filename, without overwriting an existing file of the same name
  (de-collide by suffix).
- FR-009: The daemon MUST reject unauthenticated inbound requests (shared-token auth).

**Target selection & toggle (CLI)**
- FR-010: The CLI MUST list candidate target machines discovered from the Tailscale
  network.
- FR-011: The CLI MUST let the user set the active target, and the selection MUST
  persist across daemon restarts.
- FR-012: The CLI MUST provide on / off / status commands controlling whether the
  watcher sends, with state persisted across restart.
- FR-013: The CLI MUST report current status: sync on/off, active target, and daemon
  reachability.

**Transport & networking**
- FR-014: All machine-to-machine and phone-to-machine communication MUST use HTTP over
  the Tailscale network, authenticated by a shared token.
- FR-015: The daemon MUST bind its HTTP listener to the Tailscale interface (not a
  public/all-interfaces address by default).

**Phone webapp**
- FR-016: The daemon MUST serve a static web page reachable from a phone browser over
  Tailscale.
- FR-017: The webapp MUST let the user choose a target machine from the tailnet.
- FR-018: The webapp MUST accept typed text and dropped/selected files and images (≤ 20
  MB) and deliver them to the chosen target (clipboard for text/image, receive folder
  for files).

**Lifecycle**
- FR-019: The system MUST ship as a single binary with subcommands for running the
  daemon and for the CLI client operations.

## Success criteria

- SC-001: Copying text on one machine results in that text on the selected target
  machine's system clipboard within 5 seconds, on both Linux and macOS.
- SC-002: A ≤ 20 MB file copied on the source arrives byte-identical in the target's
  receive folder with its original name.
- SC-003: Content over 20 MB is never transmitted, and the user can see it was skipped.
- SC-004: Toggling sync off stops all sending within one clipboard change; toggling on
  resumes it — verified by observing the target.
- SC-005: The active target and on/off state survive a daemon restart.
- SC-006: A phone on the tailnet can, via the webapp, deliver an image and a text string
  to a chosen target's clipboard.
- SC-007: No echo loop occurs: sending A→B does not cause B to send the same content
  back to its own target.
- SC-008: Inbound requests without the shared token are rejected.

## Out of scope (v1)

- P2P gossip / multi-peer fan-out (v1 sends to exactly one selected target).
- Clipboard history / ring buffer / anti-entropy pull.
- Bubbletea SSH TUI and the `ssh clip@host` experience.
- iOS Shortcuts tiers, OSC 52, native app.
- Anchor nomination.
- Windows clipboard backend (interface may leave room, but no implementation).
- Auto-start/service installation (systemd/launchd units), packaging, auto-update.
- HTTPS/TLS (relies on Tailscale's encryption for the link).

## Assumptions

- **Language/runtime:** Go, single static binary (locked by DESIGN.md). Cross-compiles
  for Linux + macOS.
- **Target discovery:** peers are enumerated via the Tailscale CLI/local API
  (`tailscale status`), since the user said targets are "sourced from Tailscale." A
  static peer config is a fallback if Tailscale enumeration is unavailable.
- **Auth token:** a single shared secret, generated on first run and stored in the
  config dir; the same token must be present on every fleet machine and is entered once
  in the webapp. Distribution of the token across machines is manual in v1.
- **File receive folder:** defaults to `~/Downloads/clippy` (configurable).
- **Clipboard backends:** Linux/Wayland via `wl-clipboard` (`wl-paste --watch`,
  `wl-copy`); macOS via `NSPasteboard` (poll `changeCount` ~250 ms). Text + image are
  first-class; "file on clipboard" detection uses the platform's file-URI type.
- **CLI↔daemon control:** the CLI talks to the local daemon over its HTTP API on
  localhost (loopback), reusing the same server; no separate unix socket in v1.
- **Webapp relay:** the webapp is served by whichever daemon the phone connects to; that
  daemon relays the payload to the chosen target over the tailnet.
- **Config location:** standard per-OS config dir (e.g. `$XDG_CONFIG_HOME/clippy`).
- **Selected target unreachable:** send fails gracefully (logged), does not crash the
  daemon or block the watcher.

## Open questions

None blocking. (Token distribution ergonomics and Windows support are deferred to later
